# Metronome

Closes [#7](https://github.com/benstreich/etude/issues/7). Reached from the **Metronome** pill on the
Practice picker and on the running-session screen — both open the same sheet, and the metronome keeps
running when the sheet closes.

## What it does

| | |
|---|---|
| Tempo | 20–300 BPM. −5 / −1 / +1 / +5 buttons and tap tempo (averages the last 5 taps; a gap over 3s starts a new count-in) |
| Time signature | 1/4–5/4, 6/8, 7/8, 9/8, 12/8. Beat 1 gets the accented click; compound meters (6/8, 9/8, 12/8) add a lighter click on each group of three. 1/4 means no accent; 7/8 stays downbeat-only since its grouping varies by piece |
| Tempo ramp | "+N BPM every M bars or seconds, until T". A target **below** the current tempo ramps down instead — the direction comes from the target, so there is no sign to get wrong |
| Outside the app | Keeps clicking with the app backgrounded or the screen locked, and the lock screen / notification carries slower · play-pause · faster buttons (±5 BPM) |

The saved tempo is what a run *starts* from; a ramp moves the live tempo only, and stopping snaps back
to the saved one. Setting the tempo by hand mid-run rebases the ramp from there and leaves the saved
tempo alone — so nudging from the lock screen during a ramp doesn't quietly rewrite your setting.

## Where the code is

| File | What |
|---|---|
| `src/lib/metronome-math.ts` | Pure arithmetic: `bpmAfter`, `describeRamp`, `tapTempo`, clamping. No React, no Expo |
| `src/lib/metronome.tsx` | `MetronomeProvider` / `useMetronome` / `useBeat` — scheduler, click pool, lock-screen wiring |
| `src/components/metronome.tsx` | `MetronomeButton` (pill + sheet) |
| `modules/metronome-controls/` | Local Expo module: the lock-screen transport |
| `assets/audio/click*.wav` | The three clicks (plain / group / downbeat), generated by `scripts/make-click.py` |
| `scripts/check-metronome.ts` | `npm run check:metronome` — asserts the ramp math |

Settings live flat on the store (`metroBpm`, `metroTimeSig`, `metroRamp*`) so the shallow
seed-merge in `store.tsx` backfills each key on its own for installs that predate them. The ramp unit
was once four values; anything that isn't `seconds` now counts bars, so a `'beats'` or `'minutes'`
left in an old install degrades quietly instead of needing a migration. Likewise a
`metroBeatsPerBar` saved by the pre-signature build is mapped to `N/4` on load.

## How the beat is scheduled

A plain `setTimeout` chain that re-aims at the wall clock every tick, so an interval that fires late
doesn't accumulate. The tempo for the *next* interval is recomputed from elapsed counters rather than
accumulated per beat — a dropped tick can't drift the ramp. If the process was suspended long enough
that the next target is over 500ms in the past, the clock resyncs instead of firing a burst of
catch-up clicks.

This is not sample-accurate; it is a JS timer. Good to a couple of milliseconds, which is under what
anyone hears against their own playing. A sample-accurate scheduler means rendering bars of audio
natively — worth it only if someone can actually hear the difference.

Clicks come from two players per sound, used alternately. Each is rewound 150ms after it fires, so the
beat itself is a bare `play()` with no `await seekTo()` in the way. Two deep is enough: the same
player only comes round again after two beats, 400ms even at the top of the dial.

## The lock-screen module

`modules/metronome-controls` is a local Expo module (autolinked from `modules/`, no `package.json`
entry needed). It exposes `show` / `update` / `hide` and emits `onCommand` with `inc` | `dec` |
`toggle`; JS decides that those mean ±5 BPM.

- **iOS** — `MPRemoteCommandCenter` (⏭ → faster, ⏮ → slower, play/pause → toggle) plus
  `MPNowPlayingInfoCenter` showing "96 BPM". It deliberately replaces expo-audio's
  `player.setActiveForLockScreen()`: both write the same now-playing info, so only one may be in charge.
- **Android** — a `mediaPlayback` foreground service whose ongoing notification carries the three
  buttons. The service also keeps the process alive with the screen off. `update()` goes through a
  static reference to the running service rather than an Intent, because a backgrounded app may not
  legally call `startService()` on API 26+.
- **Web** — a no-op stub, so callers need no platform checks.

It is loaded with `requireOptionalNativeModule`, so in Expo Go — where the native half isn't built —
the module is `null`, every call is skipped and the metronome still works in-app.

### Not verified

The native halves have never been compiled: this repo has no `android/`/`ios/` (CNG), and no dev
build exists yet. **Everything above the native boundary is verified** — ramp up, ramp down, target
clamping, stop-resets-tempo and the UI were all driven in a browser against the real app. The Kotlin
and Swift are unproven until someone runs:

```
npx expo prebuild --clean
npx expo run:android        # or: npx eas build --profile development --platform android
```

Expect the usual first-build fixes there. On Android 13+ the notification only appears once
`POST_NOTIFICATIONS` is granted; the metronome asks for it (via expo-audio's
`requestNotificationPermissionsAsync`) the first time it starts.

### Known ceilings

- The Android notification is a plain ongoing notification, not a `MediaStyle` one — it shows the
  buttons but not the compact media layout. Making it media-styled means owning a `MediaSession`.
- `interruptionMode: 'doNotMix'` is required for the lock screen to be ours, so starting the
  metronome will duck/stop other apps' audio.
- Recording sets the audio mode too; `practice.tsx` passes `shouldPlayInBackground: true` there so
  starting a recording can't cut off a metronome that is already running in the background.
